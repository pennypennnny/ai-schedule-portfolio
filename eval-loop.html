AI 评测闭环 · 完整迭代文档

AI 识别四轮迭代 · 完整过程还原

本文从 PRD、评测报告、项目记忆中还原 AI 课表识别的完整迭代过程，包括评测体系搭建、四轮策略动作、Bad Case 归因、剩余问题。

一、起点：为什么要做这套评测体系

1.1 问题背景

课表截图 AI 识别功能上线后，首版 Prompt 条目召回率只有 41.7%——108 节课里只有 45 节被正确识别，超过一半的课要么漏掉、要么字段错。这样的准确率用户根本没法用。

1.2 核心理念

没有度量就没有优化。
第一件事不是改 prompt，是先建评测集。如果不知道改完是变好还是变坏，迭代就是瞎试。

二、评测体系搭建

2.1 测试集构建

维度说明
规模10 张真实课表截图
覆盖类型App 周视图网格课表、教务系统网页表格课表
难度分布带钟表时间 / 仅节次；课程密度 1~35 节不等；含浮层遮挡 / 边缘裁切的困难样本
标准答案逐格人工转录，存放在 eval/truth/01.json ~ 10.json
总课程数108 节课

为什么要人工标注？ 因为没有 ground truth 就无法判断模型输出的对错。标注本身是一次性投入（10 张图约 2 小时），但后续每轮迭代都可以复用。

2.2 批量评测脚本

文件：eval/batch_eval.js

工作流程：

  1. 读取 eval/images/01.jpg ~ 10.jpg
  2. 逐张调用云函数 /parse-schedule 接口
  3. 拿到识别结果 JSON
  4. 与 eval/truth/对应.json 逐条比对
  5. 统计指标 + 输出 Bad Case 报告

为什么用脚本而不是人工？ 手动跑 10 张图要 20 分钟，脚本跑完 < 1 分钟。每轮迭代必须全量回归，人工跑不起。

2.3 评测指标定义

指标定义为什么重要
识别成功率返回有效 JSON 数组的比例接口是否稳定
条目召回率标准答案中被正确识别的课程比例（星期+节次/钟表时间匹配，有钟表时间优先用时间）核心指标：有多少课被找到了
内容识别率课程名和星期都对、仅时间字段格式不一致的宽松比例区分「内容对但时间格式错」和「完全认错」
字段准确率命中条目内 course/teacher/location/time/endTime 全对的比例，节次归一化后匹配找到的课里有多少字段全对
平均/最慢耗时单张截图从上传到返回结果的时间用户体验

🔴 基线（首版 Prompt）

策略：6 字段输出（day/time/course/teacher/location/endTime），temperature 默认。

结果：

  • 条目召回率 41.7%（108 节课只识别对 45 节）
  • 字段准确率 92.8%

Bad Case 归因（跑完第一轮评测后分析）：

错误类型占比具体表现
时间字段留空或乱猜60% (6/10 张图)有钟表时间的课，time 字段要么空、要么输出成「上午」
有钟表时间却输出成节次25%明明图上写了 08:00，模型输出「1-2节」
截断文字被补全10%「形势与政策...」被模型补成「形势与政策-5」
其他5%形近字、漏识别

核心洞察：

模型最大的问题不是「看不清」，是「不知道该怎么填字段」。prompt 没说清楚「有钟表时间就填时间、没有才填节次」这个规则，模型在两种格式之间摇摆。

🟡 第一轮：明确时间规则

策略动作：

  1. Prompt 加规则：「有钟表时间 → 填 HH:mm；无钟表时间 → 填节次（如 1-2节）；禁止推测编造时间」
  2. Prompt 加规则：「截断文字按显示原样输出，禁止自行补全省略号」

结果：

  • 条目召回率 41.7% → 67.6%（+25.9%）
  • 字段准确率 92.8% → 89.4%（-3.4%）

Bad Case 归因（第二轮评测后分析）：

  • 召回率提升明显，但还不够——还有 30% 的课没识别对
  • 新发现的问题：优先级冲突。模型看到一张课表里既有钟表时间又有节次标签时，不知道该用哪个，有时输出节次、有时输出时间
  • 字段准确率反而下降，说明规则变多后模型在字段格式上更混乱了

核心洞察：

光说「有钟表时间就填时间」不够，模型会在「有钟表时间」和「节次标签也存在」之间犹豫。必须用强制优先级锁死。

🟢 第二轮：优先级锁死 + temperature=0

策略动作：

  1. Prompt 加强制优先级：用「必须」「只有当…完全没有…才…」等表述，明确：有钟表时间必须输出钟表时间，只有完全没有钟表时间时才输出节次
  2. 加 temperature: 0，最大化输出确定性

结果：

  • 条目召回率 67.6% → 97.2%（+29.6%，最大跃迁）
  • 字段准确率 89.4% → 81.9%（又降了 7.5%）

为什么字段准确率反而降了？

  • temperature=0 让模型更确定，但也更容易「一条路走到黑」——某个字段一旦看错，不会犹豫修正
  • 但召回率的飞跃证明优先级锁死是对的方向

验证稳定性：

第二轮后连续运行两次评测，核心指标波动 < 1%，说明 temperature=0 确实消除了随机波动。

Bad Case 归因（第三轮评测后分析）：

  • 召回率已经 97.2%，剩下 3 节课漏识是因为被遮挡/边缘裁切
  • 字段准确率低的主要原因：节次和钟表时间混存在同一个 time 字段里
  • 比如模型输出 time: "08:00"，但标准答案是 period: "1-2节"
  • 前端解析时不知道这个字段到底是时间还是节次，导致保存被拦、展示混乱
  • 评测脚本按 canonical 归一化匹配，但前端逻辑无法兼容

核心洞察：

问题不在模型，在数据模型设计。time 字段同时承载「钟表时间」和「节次」两种语义，这是架构层面的缺陷。必须拆分字段。

🔵 第三轮：关闭推理链（thinking disabled）

背景：

这一轮不是为了提升指标，是为了解决稳定性问题。
用带推理能力的模型（doubao-seed-2-1-turbo）时，识别信息密集的课表截图，模型的思维链会持续生成停不下来，导致请求挂死超过 180 秒，撞上 SCF 60 秒超时。

策略动作：

  • 在 /chat/completions 请求体加 thinking: { type: 'disabled' }，关闭思考模式

结果：

  • 条目召回率 97.2%（保持）
  • 字段准确率 81.9% → 89.0%（+7.1%，两次运行平均）
  • 耗时从 >180s 挂死 → 8~10s 返回

核心洞察：

推理模型的思维链对「信息密集的结构化提取」是负担，不是助力。简单任务不需要思考，直接输出更稳更快。这个发现直接让功能从「不可用」变成「可用」。

🟣 第四轮：period 字段拆分

策略动作：

  1. Prompt 输出字段从 6 个改为 7 个：新增 period 字段专门存节次，time/endTime 只存钟表时间
  2. 配套改造：
  • 评测脚本按 canonical 规范化对比（旧格式自动兼容）
  • 10 份标准答案一次性迁移为新格式（108 节课中 62 节为节次型）
  • 前端 format.js 解析逻辑同步更新

结果：

  • 条目召回率 97.2%（无回退，波动在 ±1% 正常范围）
  • 字段准确率 89.0% → 92.4%（+3.4%）
  • 前端保存/展示逻辑彻底清晰，不再有「time 字段到底是时间还是节次」的歧义

核心洞察：

这一轮验证了「架构改进可以同时提升准确率和可维护性」。拆分字段不是为了指标好看，是为了让数据语义清晰——准确率提升只是副产品。

五、可复用方法论（从这次迭代沉淀）

5.1 AI 评测闭环五步法

收集样本 → 人工标注 → 批量评测 → Bad Case 归因 → 策略迭代 → 全量回归
    ↑___________________________________________________________↓

5.2 关键经验

  1. 先建评测集再改策略：没有度量，所有改动都是赌博
  2. 归因比改参数重要：每轮迭代后先分类统计错误类型，再决定下一轮改什么
  3. 架构改进 > 参数调优：字段拆分带来的准确率提升（+3.4%）比任何 prompt 微调都持久
  4. temperature=0 + 关闭推理链：对结构化提取任务，确定性 > 创造性
  5. 全量回归防此修彼坏：每轮改完必须跑完整 108 节课测试集，不能只看几张图

5.3 迁移到其他场景的适用性

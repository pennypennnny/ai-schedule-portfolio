一、AI 视觉识别评测闭环（核心亮点）

问题：首版 Prompt 条目召回率仅 41.7%，超过一半课程被漏识或错识。

我的评测框架：

环节做了什么为什么这样做
① 构建评测集收集 10 张真实课表截图（不同学校/排版/清晰度），人工标注 108 节课 作为 ground truth，每节课含 day / period / time / course / teacher / location 六字段没有标注集就没有度量，标注集必须覆盖真实坏样本（模糊/手写/跨栏）
② 写批量评测脚本Node.js 脚本自动调用云端识别接口 → JSON 标准化 → 与标注集逐字段比对 → 统计召回率 / 字段准确率 / 坏案例分类手动跑 10 张图要 20 分钟，脚本跑完 < 1 分钟；每轮迭代必须全量回归，防止此修彼坏
③ Bad Case 归因每轮迭代后对错误分类统计：漏召回 / 字段错 / 时间错 / 编造信息归因比盲目改参数重要——第二轮发现 70% 错误是「时间字段与节次混存」导致，直接决定下一轮策略方向
④ 策略迭代 + 回归四轮迭代，每轮改完跑全量回归，波动 > 2% 时暂停分析防止修一个 case 坏三个；第三轮改 temperature=0 后连续跑两次，召回率稳定在 97%+，才确认方案

迭代过程与数据：

轮次策略动作条目召回率字段准确率关键洞察
基线首版 Prompt（6 字段，temperature 默认）41.7%81.9%模型把有钟表时间的课也输出成节次
第一轮明确时间字段规则（优先钟表时间，禁止编造）67.6%84.3%规则约束有效果但不够
第二轮拆分 period/time 为独立字段 + temperature=097.2%90.1%字段拆分解决了混存问题；temperature=0 消除随机波动
第三轮关闭推理模型思考链（thinking.disabled）97.2%92.4%顺带解决了 >180s 超时挂死，耗时从 180s+ → 8-10s
第四轮Prompt 扩 8 字段 + 节次解析三层降级97.2%（回归无回退）92.4%新功能不影响核心指标，验证了框架稳定性

可复用方法论：这套「标注集 + 批量评测 + Bad Case 归因 + 全量回归」的框架，换任何 AI 能力（搜索排序 / 对话生成 / 推荐）都能直接重跑——工具从 Node.js 换 Python/SQL，逻辑不变。

二、LLM 对话可靠性评测与策略

问题：Agent 灰度测试时发现经典缺陷——历史复读幻觉：用户说「取消补课」，Agent 回复「好的已取消」；用户再问「补课取消了吗」，Agent 复读「已经取消过了」但实际上从未调用取消工具。

我的评测与策略：

步骤动作效果
① 定位根因检查对话历史 → 发现模型把自己上一轮的回复（「已取消」）当成了事实依据，而不是去查课表 JSON不是工具调用能力问题，是状态源错位问题
② 第一层防线服务端在 history 里只存【已执行:add_makeup_class】事实标记，不存模型的自然语言回复减少历史噪音，但不够——模型可能忽略标记
③ 第二层防线系统提示锚定：「课表 JSON 是状态唯一依据，对话历史里空口声称的安排不可信」模型开始查 JSON 了，但偶尔还是偷懒
④ 第三层防线服务端意图检测兜底：正则匹配用户有「安排/取消/调课」意图，但上一轮模型没调工具 → 强制注入纠正 prompt 让它再跑一轮彻底根治——三类防线覆盖了「历史污染」「凭空生成」「该调工具没调」三种独立失败模式

评测方法：设计 20 组对话用例（覆盖补课/调课/取消/重复确认等场景），每加一层防线跑一遍，统计「意图识别准确率」「工具调用率」「状态一致性」三项指标。最终工具调用率从 72% 提升到 100%。
